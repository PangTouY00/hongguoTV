# 红果 TV 0.1.26

版本：`versionName 0.1.26` / `versionCode 67`，支持 Android 6.0 及以上（minSdk 23）。覆盖安装即可，账号、收藏、观看进度与本机缓存记录都保留。

这一版做两件事：把「已播完」面板里真正的下一季单独标出来，以及把播放取址里那一笔每次都付、每次都白付的重复请求去掉。

## 一、已播完面板：接着看哪一季

**现象。** 一部剧播完之后，面板把同一系列的每一季都写成「下一季」。三季并列时看不出该接着看哪一部，点错一季就跳到了隔开的季上。

**改法。** `NextWorks.plan` 先算出当前这一部是第几季：标题里没有季号就当第一部，带「第2季」「第二季」按读到的算（`seasonNumber` 同时认阿拉伯数字与中文数字）。季号的读取统一成一处 `seasonOf`：先看接口 `tag_info` 给的 season 字段，读不到再看标题，排序与判定共用同一份结果，不再一处按字段、一处按标题。

只有季号正好等于「当前 + 1」的那一条记进 `nextSeasonId`。隔了一季的、季号读不到的、那一季还在待上线那一组的，都不标——宁可不标，也不把一部隔了两季的剧指成「接着看」。

面板行的区分同时走三样：文字、加粗、颜色。真正的下一季写成「接着看 · 第2季 · 剧名」，其余同系列的季写成「其他季 · 第3季 · 剧名」。`TvTools.choose` 新增 `emphasis` 参数，对这些行用强调色并加粗。不只靠颜色：系统给列表项的焦点态会换底色，电视上色觉也各不相同，只靠颜色在那一刻分不出来。

## 二、播放取址：那条兼容请求只问一次

**现象。** 五集连播的实机日志里，一集的所有清晰度都是厂商私有编码（bytevc1）时，取址会在 v5 之外再发一条 `codec_type=0&force_codec=h264` 的兼容请求，要一份系统播放器能解的档。它五次全回 HTTP 200 + 0 字节，一次 0.9～1.8 秒；而最终播通的恰恰是 v5 给的那份 1080P bytevc1。

它占掉的份额不小：首页四次试播的取址耗时里 32%～47%，正式播放那一次占取址总耗时的 68%。整段日志里只有这一处是付了钱什么都没买到。

正式播放那一集的首帧 7673ms 拆开是：

| 阶段 | 耗时 |
|---|---|
| 设备注册 + v5 取址 | 847ms |
| 全档私有编码 → 兼容请求（失败） | 1787ms |
| 打开流（读首段 + MP4 索引） | 3148ms |
| 首帧 | 1759ms |

**改法。** 同一件事只问一次，两种情况下不再重复问：

- 这一集给的私有编码里，有一种在这台设备上真渲染出过首帧。新增的 `CodecMemory` 记下它，app 层接到设备能力记录同一份存储的 `playable` 集合，跨重启保留。写入时机只有 `onRenderedFirstFrame`——记的是这一集实际用的那一种编码，不是接口下发的某一档，也不是 `MediaCodecList` 报出来的能力表。跳过时日志写「本机已实测这种编码能播，不再要兼容档」。
- 这条兼容请求刚刚失败过（进程内 10 分钟冷却）。跳过时日志写「兼容请求刚失败过，这一轮不再问」。

冷却过期后照旧再问；换到一种这台设备没试过的私有编码时也照问。选档本身仍然不预判设备能力，这条改动只去掉重复请求，不改变选哪一档。

**取址日志写的是那次请求的事实。** 成功那一行原来照轮次写「账号Cookie=带」，而实际成功的是 v5 那条，它强制不带任何 Cookie（`CookieJar.NO_COOKIES`）；同一轮里兼容请求那一条又硬编码成「不带」，而它其实带着账号 Cookie。现在写的是实际成功的那条请求带没带 Cookie、清晰度来自哪条接口。

**起播缓冲门槛 1000ms → 500ms**，与首页试播用同一个值。播放中途 rebuffer 的门槛保持 2000ms 不变。

## 没改的两处，以及一处没动的大头

- 失败重试的节奏没动：取址内部最多四轮、每轮换一份新注册身份，轮间等 700 / 1400 / 2100ms；播放失败自动重试三次，间隔 1000 / 2500 / 5000ms。那段日志里它们一次都没触发。
- 首段读 256KB 没砍。首页试播读 32KB 只要 272～728ms，看着像可以砍，但那 256KB 里除了 MP4 索引全是样本数据，播放器首帧本来就要用；砍了只是把等待从取址挪到播放器，还多付一次 range 请求的首字节。
- 首帧那 1759ms 主要是吞吐不够：按 256KB/3148ms 与 32KB/272ms 反推，当时链路吞吐约 100～150 KB/s，而 1080P 一秒的样本就要 190KB 以上。代码解决不了，除非首帧先落到低档再升——那改的是画质策略，这一版没动。
- 首页 `Home recommendations` 2068～4680ms，日志里没有 `Home starter-cache hit`，启动缓存没生效。这是首屏最大的一块，和播放取址是两件事，这一版没碰。

## 验证

新增 6 项 core 单测覆盖下一季的判定：当前季号、隔季不标、待上线不标、字段缺失时从标题读、「第2季」与「第二季」都认。另新增 6 项覆盖兼容取址的记忆：失败后跨集不再问、真播通过过的编码不再问、接口写大写也算同一种、冷却过期后重新问，以及取址成功那一行必须写实际成功那条请求的 Cookie 与接口来源。

GitHub Actions 运行 `:core:test`、`:app:testDebugUnitTest`、`:app:lintDebug`、`:app:assembleDebug`、`:app:assembleRelease`，全部通过后才发布本包。

## 怎么验证

1. 播完一部多季的剧，看「已播完」面板：该接着看的那一季写「接着看 · 第N季」并且加粗、上色，其余季写「其他季 · 第N季」。如果这一季和当前季隔开了，它不该被标成「接着看」。
2. 连播两集以上，设置 → 诊断日志 → 复制，看第二集起有没有出现「本机已实测这种编码能播，不再要兼容档」或「兼容请求刚失败过，这一轮不再问」。有这一行，取址就该短 1 秒上下。
3. 起播门槛降到 500ms 之后，注意会不会更容易起播即卡。若卡，这一项会单独退回 1000ms，其余保留。
