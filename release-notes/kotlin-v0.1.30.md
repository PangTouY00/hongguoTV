# 红果 TV 0.1.30

版本：`versionName 0.1.30` / `versionCode 71`，支持 Android 6.0 及以上（minSdk 23）。覆盖安装即可，账号、收藏、观看进度与本机缓存记录都保留。

这一版有四件事：两处修站方 2026 年 11 月下旬的接口变化（一处让**点开任何一集都进不去**，一处让**取址又全空**），一处修后备取址通道一直取不到清晰度，另加播放界面右上角的当前时间。

## 一、点开任何一集都进不去：官网详情页不再下发全集 id

**现象**：首页、榜单、搜索、详情卡片都正常，点进剧集以后每一集都被拦下，提示「分集数据异常」。

2026-11-27 起，站方官网详情页 `detail?series_id=` 里的 `seriesDetail.vid_list` 由「全集的纯数字分集 id」换成了**只有 3 条的 `v1_` 混淆串**，而同一页的 `episode_cnt` 仍然写着 300。本机与上游拿到的都是 3 条。原来的校验要求这一串全部是纯数字，于是每一部剧都被判成数据异常——首页正常、一集都进不去。

**改法**：剧集元信息继续走官网详情页，分集退回站方 App 自己在用的目录接口 [`/reading/bookapi/directory/all_items/v/`](kotlin-tv/core/src/main/kotlin/com/hongguotv/core/ContentRepository.kt)。这条接口只要 v4 那一族签名，不需要注册设备、不需要账号，也不消耗发号配额。它有两种响应形态——带 `code=0` 的，和没有 `code` 字段但 `message=SUCCESS` 的——两种都接受；只要任何一条分集 id 不是纯数字就整条不采用，仍然回落到「分集数据异常」。官网详情页如果哪天恢复下发全量纯数字 id，代码仍然优先用它，这条回退只在站方改动生效时才走。

**实测**：首页现取的 12 部真实剧集，全部给出全量纯数字分集（88 到 1000 集），与详情页自称的 `episode_cnt` 一致。另加两条分集回退的回归测试。

## 二、取址又全空：站方只接受补全后的 medusa 设备信封

0.1.29 修的是 medusa 明文的第 21 个字段（377 → 312）。那之后能取一段，2026-11-23 起又一律回 `HTTP 200 + 0 字节`——现象和上一版一模一样，根因换了。

这次被拒的是**设备信封**：旧形态只有 14 项设备字段、flags 全 0、没有 field 16，站方把它静默封锁成「请求合法但不给数据」。跟随上游 N3urda/hongguoTV PR #122（2026-11-26 合并）补全：

- flags 换成 `4480000000000000`；
- 设备字段补到 field 38 为止共 36 项（含品牌、机型、时区、语言、系统版本、几个固定整数与几个 0 值浮点）；
- `f5` 与 `f16` 用首位固定为 `A` 的 25 字符设备令牌；
- `env` 段连同其中嵌套的 `deviceInfo` 换成现行形态（启动序号、进程号、渠道、版本名、一段内层时间戳）；
- field 15 的四个数值换成真实观测值。

第 21 字段仍然是 312。同一份新注册身份、同一集做 A/B：312 一路 `code:0`、各五档清晰度含 `1920×1080`；换回 377 照旧 0 字节。签名固定向量改用上游按 PR #122 形态从同一份 312 向量重新封装的 [`signing-v5-playback-envelope.json`](kotlin-tv/core/src/test/resources/signing-v5-playback-envelope.json)，逐字节对拍通过，换回旧信封形态即不一致。

要说清楚的是：这组字段在实测里把空响应恢复成了完整模型，但**尚未逐项证明每一个字段都是必需的**——补全后的信封是「已验证够用」，不是「已验证每项都必要」。

## 三、后备取址通道 `/player/v1` 一直回空：少了一个 query 参数

2026-11-24 在 Debian 的 dev34 模拟器里用 Frida 抓到官方红果 7.4.5.32 沉浸式播放页真实发出的取址请求：`POST …/novel/player/multi_video_model/player/v1`，host 与 path 和我们完全相同。随后用对照探针（同一份新注册身份、同一集、同一签名与正文，每路只改被检的那一项）逐项二分，结论是这条接口只多要一个 query 参数 `manifest_version_code`：

- 带上它：一律 `code:0`、五档清晰度；
- 去掉它：一律 `HTTP 200 + 0 字节`；
- 其余二十项公共参数（设备描述、业务开关）整组删掉照样给完整模型；正文压不压缩、设备 Cookie、版本号取什么值都不是变量。

之前把这条接口的一律回空归到域名、path 写法或签名族，都是这个缺失参数造成的假象，[PLAYBACK_DIAGNOSIS.md](kotlin-tv/PLAYBACK_DIAGNOSIS.md) 已同步更正，这组对照实验留在 [`tools/probes/AppShapeProbe.kt`](kotlin-tv/tools/probes/AppShapeProbe.kt)，可以一次重跑。

## 四、播放界面右上角显示当前时间

看剧时想知道现在几点，但屏幕上没有地方能读到。它属于播放器 HUD 这一组东西，所以显隐不给它自己的开关：标题、进度条、控制面板和时钟统一走 `setHudVisible` 这一个入口，不会出现进度条亮着而时钟灭掉的状态。播放中无操作自动收起仍是原来那 4.5 秒；暂停、失败面板、选集面板开着时 HUD 不收，它也不收。

屏幕上是纯数字、不铺任何底色，字号比剧集标题更大一档（电视 28、手机 20）；数字走等宽字体，免得分钟位一变整块宽度就跳；12 还是 24 小时制跟系统的区域设置走，不在 App 里另设开关。纯白数字落在浅色画面（白墙、天空、雪花屏）上会糊，所以只留一圈柔和的深色投影把字形托出来——文字阴影在 API 28 以下不与硬件加速共存，本包最低 API 23，这块控件显式走软件层以保证各机型表现一致。起播时和其他控件一起创建，`releasePlayer` 时一起从视图树上摘掉。

## 验证

- core 单元测试通过，包含两条新的分集回退回归与换形态后的签名固定向量。
- 本机端到端探针（验证的是分集与取址，不是画面）：三部剧分别 300 / 102 / 1000 集全部列全，每集取到含 `1920×1080` 的五档清晰度与真实 `main_url`。
- GitHub Actions 在合并提交 `1da3446` 上跑 `:core:test`、`:app:testDebugUnitTest`、`:app:lintDebug`、`:app:assembleDebug`，全部通过后才构建发布本包。
- **真机画面与分集显示尚未装机验收。** 本机验证到的程度是「列全分集、取到五档清晰度和真实地址」，画面能不能出来、明亮场景下那个时间读不读得清，要看装机。

## 怎么验证

1. 之前提示「分集数据异常」、一集都点不进去的剧，现在应当能列出全集并开播；集数多的那几部看列表是不是拉到底。
2. 之前播不了的那几集，现在能不能出画面、清晰度里有没有 1080P。
3. 播放中按遥控器调出进度条，右上角应同时出现当前时间；停手 4.5 秒后它和进度条一起消失。
4. 若仍失败，打开设置页「诊断日志」复制出来发我，那里面会写明这一轮取到了哪几档、或者服务端回了什么状态码和字节数。
