# 红果 TV 0.1.10 更新说明

这一版做四件事：手机号登录现在真的能登录了；用移动数据看剧时下一集也会提前打开；播放地址偶发取不到时先重试而不是直接判整集失败；排行榜在启动后就在后台读好，走到那一页不再空等。

## 手机号登录：接上平台要求的上行短信二次验证

0.1.9 里我们说手机号登录「平台不签发登录会话」。那次判断不完整。真实号码、真实短信重测之后跑通了完整链路：

`send_code(type=24)` 取到 `mobile_ticket` → `sms_login` 提交验证码 → 平台通常以 `error_code 2046` 要求身份验证，并在 `verify_ways` 里写明**用哪个号码、发什么内容、到哪个号码** → 用户用手边的手机发出那条短信（电视本身没有 SIM 卡）→ 客户端按官方验证页的节奏轮询 `/passport/upsms/verify/` 取回验证票 → 在同一会话里带这张票完成登录 → 平台签发 `sessionid`。

据此调整：

- 验码端点从 `validate_code` 改为 `sms_login`。前者对第三方客户端只回「会话过期」，后者才是这条通道真正使用的端点。
- 账号界面会照原样显示要发送的短信内容与号码，并有「我已发送」确认；确认后自动继续，不需要重新输入手机号。
- 身份验证通过后**先带票重放刚才那张验证码**，而不是重新发一张。`2046` 与 `upsms/verify` 的响应里都换发了新的 `mobile_ticket`，而平台把验证码留着（`biz_params.sms_code_key`），重放通过就直接签发会话。
- 只有平台回 `1203` 说那张码作废时才重新发一张，并且先等满平台的发码冷却：成功发码时平台回 `retry_time`（实测 60 秒），没到点再发会回 `1206 验证码发送太频繁`。客户端先等满冷却再发、被拒后再等一轮、只重试一次，并把要等的秒数显示在屏幕上，等待期间用提示条说明在等什么。此前出现过「第一张码通过、上行短信也发了，第二张码被 1206 拒掉，界面停在『验证码没发出去』」的情况，前面做的身份验证白做。
- 带票重放仍被拒时不再继续引导发第二条上行短信。这条短信按运营商计费（一般 0.1 元/条），第一次被拒还允许再试一次，第二次起界面落到「改用扫码登录」。
- 平台只给抖音侧验证方式时不硬编成手机号可用；扫码登录仍是始终可用的路径。

## 自动连播：移动数据下也提前打开下一集

之前的预取前提里有一条「蜂窝网络直接不预取」。用移动数据看剧时这条路径从不启动，切集只能走完整的重新取址、读索引和 prepare，所以每集都要在画面出现前等一次网络往返。

现在按网络类型分级：移动数据预热 1 MiB（Wi-Fi 仍 2 MiB）、在剩余 60 秒内开始（Wi-Fi 仍 30 秒）、缓冲领先门槛 2.5 秒（Wi-Fi 仍 5 秒）、每集至多 4 次尝试与 8 秒冷却（Wi-Fi 仍 3 次与 15 秒）。电视与 Wi-Fi 的参数没有改动。

另外：网络能力变化（Wi-Fi 与移动数据之间切换）不再取消已经预热好的下一集，只有真正断网才取消；切到下一集时若该集的预热仍在进行，最多等 1.5 秒复用它，而不是再取一次地址、再读一次索引，复用时也不会为同一集开第二条连接。

## 播放地址偶发取不到时先重试

手机实测自动连播时，有一集连续三次 `EmptyContentException` 才播起来，屏幕上显示「准备恢复暂停位置 · 5.0 秒后重试 3/3」。这个异常来自客户端自己：播放地址接口偶发返回 HTTP 200 但响应体为空，与榜单页被 CDN 软拦截是同一类现象。取播放地址那条请求恰好是少数没有开启有限重试的只读请求（榜单、搜索、分类都有），于是一次空响应直接冒泡成整集播放失败，只能靠 App 层的自动恢复兜底，代价是重建播放器和十几秒等待。

现在主接口与 legacy fallback 都对空响应、超时与 5xx 先做至多两次同一查询的重试，仍然失败才报成播放失败；被切集或导航取消的请求不重试。日志同步修正了两处误导：下一集在本集切换生效前就渲染出首帧时，不再被记成当前集「21 秒才出画面」；预热没落地时也区分「被切集取消」和「真的取址失败」。

## 排行榜：启动后就在后台把榜单读好

本机记录读完成、首屏出现约 4 秒后，客户端在后台把榜单读进同一份会话缓存：Wi-Fi 预读四个榜单，移动数据只预读当前默认榜，其余榜单留给用户真正打开时再读，避免后台跑掉二十页流量。预取与排行榜页共用同一个状态机，同榜在途自动去重，所以预取不会和切榜、手动刷新互相重复，也不会互相取消。

走到排行榜时通常已经有内容。如果预取还没完成，界面照常显示正在准备，完成后会直接把数据补到当前画面上，不需要按刷新；预取失败时标注「后台预取未成功 · 按右上方刷新重试」，旧榜单（若有）继续保留。预取只写内存里的会话缓存，不落盘，TTL 仍是 10 分钟。logcat 搜索 `Rank prefetch` 可以看到预取了几个榜、每个榜拿到多少部、读了几页以及失败原因。

## 兼容与验证

- 仍是单一 APK：minSdk 23（Android 6.0 及以上），versionName 0.1.10 / versionCode 51，包名与签名与 0.1.9 一致，已装 0.1.9 的设备直接覆盖安装并保留本机数据。
- 修掉一处只在测试里出现、但会拖垮整条检查的问题：`PreparedSlot.await` 的超时读的是注入时钟，而 Robolectric 的 paused looper 会把 `SystemClock.elapsedRealtime` 固定不动，于是这个等待永不结束，`:app:testDebugUnitTest` 挂到被 CI 超时取消。等待预算改用真实单调时钟，注入时钟只负责结果新鲜度；并新增一条用例锁住这个回归。
- CI 的 Gradle 缓存补上 `~/.m2`，Robolectric 的 android-all 镜像不再每次重新下载。
- CI 跑 `:core:test`、`:app:testDebugUnitTest`、`:app:lintDebug`、`:app:assembleDebug`。Robolectric 在 API 23 与 API 26 上验证：`2046`→上行短信→取票→带票完成登录整条链路、只给抖音验证时不硬编、`1203` 重新发码、发码冷却与等待通知、带票重放不再发码；移动数据仍预取、复用进行中的预热、预热不落地时及时取消；空响应会被重试且重试次数有界；预取已占住的榜不会被二次请求，且预取完成后正在显示的榜立刻有内容。
- 手机号登录的上行短信、排行榜预取的实际观感、移动数据下的切集衔接仍需装机确认。
