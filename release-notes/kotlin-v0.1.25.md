# 红果 TV 0.1.25

版本：`versionName 0.1.25` / `versionCode 66`，支持 Android 6.0 及以上（minSdk 23）。覆盖安装即可，账号、收藏、观看进度与本机缓存记录都保留。

这一版做两件事：播放取址改用 v5 签名协议，以及把播放过程写进可以在设备上直接取出的诊断日志。

## 现象

2026-11-16 起所有集都播不了。取址每一轮都是 HTTP 200 + 0 字节，换一份新注册身份、换 Cookie 形态都不改变结果，而首页、搜索、榜单全部正常，官方 App 在同一张网络上能播。

## 根因是签名协议落后

对照只换签名这一个变量：同一条 path、同一份新注册匿名身份、同一集号、同一 gzip 正文——

| 签名 | 同一条接口的响应 |
|---|---|
| 旧签名 | HTTP 200，正文 0 字节 |
| v5 签名 | HTTP 200，正文 24345 字节，业务码 0，含五档模型 |

这条对照在本仓库里保留着：正式路径走 v5，旧签名在 `ContentRepository.legacyStreamLadder` 里只供离线回归。两条各跑一次，正文从 0 字节变成几 KB 就证明是签名问题。

## 改法

**签名与请求结构。** 播放取址改用 v5 签名协议与 gzip JSON，签名绑定实际压缩字节、最终请求票据与当前匿名身份；目录、搜索等仍用原有签名，不受影响。协议常量、签名结构与合成测试向量取自 [N3urda/hongguoTV](https://github.com/N3urda/hongguoTV) 固定提交 `6672b55d5308ea1ec26d2fe0bc0b2401ef4aa0c3`（GPL-3.0-only），没有引入第三方 VM、原生 SDK 或远程签名服务。移植完先离线对拍再联网：4 条 AES v5 carrier、32 条 `hashF13`、32 个连续时间戳的 `signPlayback` 与上游向量逐字节一致。

**同一条接口的两种写法，当场切换。** 同一个 host、同一份正文、同一套签名，path 有两种写法，服务端对它们的反应不一样：

| 写法 | 实测（三个域名各试一次，每次用新注册身份） |
|---|---|
| `/novel/player/multi_video_model/player/v1` | 一律 HTTP 200 + 0 字节 |
| `/novel/player/multi_video_model/v1/` | 一律 code=0，五档 `main_url` + `spade_a` |

所以当前写法没有结果时，取址会当场换另一条再要一次：用的是同一份设备身份、同一份正文、同一套签名，只有 path 不同。触发条件是「这条写法没给出结果」——HTTP 200 空正文、404、5xx、连接失败；业务码非 0（`110001` 那类账号侧拒绝）与响应结构不对不触发切换，因为换过去结果一样。两条都不给结果才接着试 `video_tab` GET 与旧 POST，顺序与原来一致。

**顺带。** 取址请求补回 `x-medusa` 与 `x-helios`，`x-ss-stub` 改用大写；多试一条 `POST /novel/player/video_model/v1/`。

**诊断日志。** 播放过程记进内存日志，设置页有「诊断日志 · N 条」一行，点一下把整份日志复制到剪贴板，同时弹窗显示最近 120 行，旁边有「清空」。取址失败会记下服务端回的状态码、响应字节数与网关 logid；播放失败记下完整原因链（每一层的类型与 Media3 错误码，最多六层）；首页试播失败与账号侧登录状态也写进去。日志不含 Cookie、令牌、账号，所以这份文本可以直接贴出来给人看。

## 验证

真机（同一台 Android 16 手机）：同一份新注册匿名身份、同一集号，v5 请求 1.1 秒回完整模型，五档 360p/480p/540p/720p/1080p 都带 `main_url` 与 `spade_a`；旧签名在同一条接口上仍是 0 字节。

**画面已真机验收。** 2026-11-17 装本分支的调试包后可以正常播放，包括只有 `bytevc1` 私有编码的那三集。这条接口给的编码写法 `force_codec=h264`、`codec_type=0`、`use_os_player=true`、`need_mp4_align=true` 四种都不改变结果，而私有编码在这台设备上解得出来——此前写在文档里的「系统播放器解不出厂商私有编码」不成立，具体走的是哪条解码路径没有查。

## 代价

当前那条写法真的不给结果时，每次取址会多花一次失败请求（实测一次约 0.3～1 秒）。诊断日志里会先出现「当前取址写法没有结果 … → 换 …」，紧接着「v5 取址成功（备用写法）」，这两行是预期行为，不是新的故障。

## 怎么验证

1. 点播放，应该直接出清晰度列表并能播。
2. 如果播不了，设置 → 诊断日志 → 点复制，然后看日志里的数字：取址回的是状态码几、正文几字节、业务码是几。这三样决定是哪一类故障，四类故障的排查顺序写在 `kotlin-tv/PLAYBACK_DIAGNOSIS.md`，v5 的移植与两种写法写在 `kotlin-tv/PLAYBACK_V5.md`。
