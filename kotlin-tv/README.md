# 红果 TV 原生客户端

工程：Kotlin + Android View。正式线同时维护两个构建，版本号一致：`main` 是 Android 6.0+ / API 23（Media3），`android44-support` 是 Android 4.4+ / API 19（系统 MediaPlayer + 只监听本机的 HTTP 代理，OkHttp 3.12、无核心库脱糖）。compileSdk、targetSdk 为 36。包名 `com.hongguotv.nativeapp`，与旧 React Native 应用 `com.hongguotv` 的数据独立。

功能介绍见 [项目主页](../README.md)，工作约定见 [开发流程](../CONTRIBUTING.md)。

## 首页刷剧

切回本次已浏览的推荐、漫剧、真人剧时恢复该来源的列表、分页和选中作品，试播从头开始；「换一批」仍请求新批次。账号变化清空三类来源状态。另有按登录身份隔离的 10 分钟首屏元数据缓存，每来源最多 30 部，仅保存卡片与经过详情核验的首集 ID/总集数；不保存播放 URL、服务端游标或凭据。缓存命中先试播缓存作品，后续分页以新的服务端会话获取并去重，过期或损坏时直接联网。

播放地址优先读官方 App 现行的 `GET /reading/bookapi/video_tab/multi_video_model/v1/`（一次一集，参数 `video_id`/`video_id_type=0`/`device_level=1`/`need_all_video_definition=1`/`need_mp4_align=0`/`use_os_player=0`/`video_platform=1024`/`source=0`/`from_video_id=` 缺一不可）；旧的 `POST /novel/player/multi_video_model/v1/` 自 2026-11-02 起对第三方客户端一律回 HTTP 200 空响应，现只作回退，回退仍未取到清晰度时就报新接口的错误码。播放模型若包含完整可用的 video_meta、encrypt_info 与媒体地址，直接选流和派生内容密钥；缺少可用项时保留原备用接口。首页先在一个 256 KiB 范围请求中消费 32 KiB，再按实际索引大小继续读取，索引超过范围时补取；正式全集播放仍采用原首段大小。首次进入、冷缓存和缺少可靠首集标识的分类仍有必要的联网请求。

首页推荐、漫剧与真人剧均试播第一集。保留下一部至第三部的播放地址与完整索引缓存（先消费 32 KiB，再补齐完整索引，不等待整个 256 KiB 范围响应）；当前视频正在播放且缓冲达到 1.5 秒后，启动下一部的预加载。完成地址和索引解析后立即交给 Media3，无需等额外固定 1 MiB 下载；Media3 提前解析轨道并将下一部约 1.5 秒的媒体样本放入播放器缓冲，后两部只提前选择轨道；播放器预加载总缓冲目标为 4 MiB。沿用一个播放实例，不为每部作品建立独立解码器。

上下换剧时复用缓存；若目标作品仍在预加载，则接续该任务，失败后退回前台加载，避免取消后重复解析与下载。同一 HTTP 分段中的视频数据边到达边交给播放器，不等待整个 512 KiB 分段完成。切换类型、换批、离开页面或退出仍取消过期任务并清理资源。

本轮参考本地官方 App 6.5.5.32 中可识别的 TTVideoEngine、DataLoaderHelper 和短视频预加载组件，采用独立实现；静态分析不能确认官方实际启用的策略或参数。Media3 接入依据 [Android 官方预加载文档](https://developer.android.com/media/media3/exoplayer/preloading-media/preloadmanager)。没有在模拟器或电视上进行速度对比，不承诺固定首帧耗时或达到官方 App 的速度。首次进入仍需要推荐、播放地址和视频索引请求，连续刷剧的效果需用户安装测试包验收。

日志只记录 `Home recommendations`、`Home category`、`Home detail`、`Home starter-cache hit`、`Home play-address`、`Home promoted in-flight preload` 与 `Home first-frame` 等阶段信息，不打印播放地址或账户信息。`first-frame` 从交给播放器开始计时，不包含此前推荐及地址请求耗时。

## 连续浏览

找剧分类接近底部时按服务端返回的偏移和会话游标继续加载，关键词搜索按服务端页码继续加载，结果均去重追加。分类和搜索遇到连接超时、连接中断、域名解析失败或 HTTP 500/502/503/504 时，等待片刻后自动重试同一请求一次；其他 HTTP 错误或响应格式异常不自动重试。仍失败时保留当前列表，底部显示错误类型并可手动重试。搜索返回分类、从详情返回列表时恢复选中作品。排行榜每个榜单页遇到连接超时、连接中断、域名解析失败、HTTP 500/502/503/504 或 HTTP 200 空响应时在瞬时失败时自动重试一次；重试后仍失败的页会跳过，副标题标注「已读取 N/M 页（部分）」并按已读取页展示，第一页失败则显示读取失败。排行榜使用六列海报网格，沿用完整榜单和全榜题材筛选，卡片标注原榜名次与可用热度，连续浏览不改变原始名次。榜单请求在内存中携带站点重定向下发的会话 Cookie（不落盘），读取使用收紧的超时（连接 8 秒、读取 12 秒、整调用 15 秒）。四个榜单各自独立并行加载、互不取消：会话内 10 分钟 TTL 内切换直接展示缓存零请求，过期后展示旧榜单的同时后台静默续期，只有点刷新才强制重拉；切换榜单不进入模态等待。本机记录读完成、首屏出现约 4 秒后，客户端在后台把榜单读进同一份会话缓存：Wi-Fi 预读四个榜单，移动数据只预读当前默认榜。预取与排行榜页共用同一个状态机，同榜在途自动去重，不会和切榜或手动刷新互相重复，也不会互相取消。预取完成时若用户正停在这个榜上，界面直接补上数据，不需要按刷新；预取失败标注「后台预取未成功 · 按右上方刷新重试」，旧榜单（若有）继续保留。logcat 搜索 `Rank prefetch` 可确认预取了几个榜、每榜拿到多少部、读了几页以及失败原因。预取只写内存里的会话缓存，不落盘，TTL 仍是 10 分钟。找剧分类页移除常驻加载／回顶按钮，接近底部自动加载，失败才显示重试；分类页按返回回顶并聚焦「找剧」，再次返回按原导航规则离开。搜索结果与排行榜保留各自原有返回和回顶操作，长按确认或菜单键管理作品。

输入停顿 350 毫秒后请求官网公开联想接口，最多显示 8 个候选；服务端可将部分拼音输入匹配为中文剧名。选中候选后按该中文词搜索，不自动打开详情；直接搜索、搜索历史与手机输入仍可使用。联想请求使用独立可取消任务，不中断当前结果分页；输入变化、离开页面或切到后台时取消过期任务，失败不阻止直接搜索。不承诺任意拼音、首字母或错别字都能匹配。

分类使用 App 分类接口的真实分组：类型（全部、真人剧、漫剧、AI 剧）、主题、设定、背景、推荐排序、受众、上新时间，以及服务端提供时的作品状态。每组单选，不同组的条件组合提交到服务端，不是只筛选已加载作品；每行「全部」清除本组条件，受众「女频」的值为 `0`，与「全部」区分。切换内容类型会清除旧类型的条件并重新获取分组，重置会回到全部类型、全部条件。

遥控器左右选择同组条件，上下切换分组；较小屏幕可上下滚动筛选区。进入海报列表保持筛选展开状态，可手动收起；列表首行向上可到筛选控制按钮；搜索或详情返回后保留组合条件、列表、选中作品及筛选行滚动位置；选中高亮始终依据实际筛选条件重绘，横向超出可视区域的选中项会恢复到可见范围。分类仍最多加载 100 批，未返回的分组或选项不自行补造。海报向下浏览一行后，搜索输入行与类型筛选行一并收起以让出整屏列表空间，回到列表顶部或焦点回到筛选条件时自动恢复；遥控器与触屏拖动都走同一条规则，此时列表首行向上直接回到「找剧」导航。排行榜、收藏、观看历史与账户预约向下浏览一行后同样收起上方的榜单标题、榜单或来源切换按钮与说明行，回到列表顶部即恢复，此时列表首行向上直接回到对应导航；首页与设置页保持原有布局不变。海报卡片按站点实际返回的封面比例测量并统一整列比例，图片铺满整列不再留两侧深色空白；首页分区、剧集详情封面与相关作品卡片同样按该比例排布，首页在首批封面到达后会自动重排一次。可用高度不足时海报缩小，标题改为单行，必要时隐藏副信息以保留列表空间；完整作品信息仍可进入详情查看。旧网页分类入口继续保留给首页兼容路径及 Mac 客户端，本轮未改变它们的行为。

界面使用 Android 系统 GridView 回收离屏卡片，搜索最多 100 页、分类最多 100 批；切换分类、题材或关键词会重新从首批读取。账户收藏、历史和预约的读取范围不变。遥控器手感仍需用户在电视上验收。

## 离线缓存

选集面板新增「缓存本集」「缓存全部」，剧集详情页的次要操作行新增「缓存全部 N 集」，按钮文字跟着状态走（「已缓存 x 集 · 缓存全部」「已全部缓存 · x 集」「缓存中 · 还有 n 集」）；播放页「播放设置 → 缓存管理」可缓存或删除当前这一集、缓存未缓存的全部、清空全部、停止队列，并给出已缓存集数、占用 MB 与剩余空间。一集在缓存里的状态直接画在集数上：`✓` 已缓存、`…` 排队中、百分比、失败；面板顶部一行给出队列摘要。播放界面状态行在清晰度后标注「本地缓存」，队列在跑时追加「缓存中 n 集」。下载进度只改格子上的文字，不重画整屏，焦点不会跳走。

缓存键是分集 id 加清晰度，不是 URL 哈希：播放地址带签名有效期，用地址做键会让同一集反复重下，也没有稳定的「删掉这一集」入口。文件存在应用自己的外部私有目录（`getExternalFilesDir`），不需要任何存储权限，代价是卸载即清，这一点写在缓存管理里；同一行还写明当前用的是外部私有目录还是应用内部目录。外部目录建不出来或写不进去时退回应用内部目录（`filesDir`），两处都是应用私有、都不需要权限。留出 512 MB 余量，一集放不下时当场拒绝并给出剩余 MB，不留下永远续不完的半截文件。剩余空间读的是缓存目录所在的那个卷：目录还没建出来时先把目录建出来再读，因为 `usableSpace` 对不存在的目录返回 0，照旧去读会把设备还剩的一百多 GB 报成「还剩 0 MB 可用」，每一集都被拒绝。目录建不出来或不可写时报的是目录本身，不会和「空间不足」混成一句。

下载一次只跑一集，按点下的顺序排队；连续三集都失败就停下整批，不再把整部剧试一遍。中断（取消、连接断开、进程被杀）留下 `.part`，下次点同一集从已写的字节继续；半截文件比这一集还长时不续传，重写。列缓存时只列出元数据声明的字节数、文件实际大小与元数据三者都对得上的记录，对不上的当场清掉；没有元数据的视频文件一并删掉，`.part` 保留给下一次续传。缓存 HTTP 通道沿用播放那一份（`newBuilder` 只放宽读超时），同一组 CDN 复用连接，注册下发的 Cookie 也一并带上。

「收藏」标签改名「收藏下载」，页面顶部三个来源各自独立：本机收藏、账户收藏、本机下载。切到「本机下载」时按剧列出已经落盘的缓存，卡片副标题写「已缓存 x 集 · y MB」，按占用降序排列；点开这部剧时直接由本地缓存拼出剧集列表，不联网也能进、能选、能播——列表只列这台设备上已经缓存下来的集，集号取自缓存元数据（缓存了第 145 集，列表第一项就是第 145 集），顶部写明「离线 · 只列出…」并给一个「加载全部剧集」的入口，联网后点它才去拉完整列表。其它入口（首页、收藏、搜索、续播）照旧先请求远端，请求失败且这部剧有缓存时同样退到这份离线列表，不会只剩一句「无法连接内容网站」。长按出现「删除本机缓存 · x 集」，确认后删除，观看进度与收藏都不变。三份列表不混排：收藏是「我想看」，下载是「已经在这台设备上」，合成一份会让「收藏了但没下载」「下载了但没收藏」两类都没法表达。

列表的归类依据是缓存元数据里新增的 `seriesId`／`seriesTitle`／`cover`／`episodeIndex`：缓存一集时把它属于哪部剧、是第几集写进去，列表按前几项归类、离线详情按最后一项排集号，都不联网、不查详情——离线列表不该因为网络不通就空掉。旧版本写的元数据没有这几项，记录仍然可用、仍然能离线播放，只是不进按剧归类的列表、集号显示成「已缓存」，页面顶部会报「另有 n 个旧版本缓存的片段认不出属于哪部剧」；之后再点一次缓存同一集会补上归属与集号，不重新下载。

缓存文件里存的是播放器实际消费的字节：改写过的容器索引，加已经解开的样本。离线播放不需要密钥、不需要再解密、也不需要网络。播放时先查本地：命中就直接本地播，不查清晰度阶梯、不发任何请求——签名过期、限流、设备注册这些在线才会出的问题都不存在。缓存档能不能解码仍走同一套 MP4 头校验，判不过就回退在线，由在线那条路去挑这台设备解得了的那一档。同一集有多档时取上限内最高的那一档；一档都不够低时取其中最低的，解码能力由校验决定而不是由清晰度设置决定。自动连播时，下一集已经在本地就不再预热：本地打开没有取址与首段网络等待，预热反而抢带宽。

自动化检查覆盖落盘与列出、按 1 MiB 分块、元数据里的剧集归属写入后读回一致、旧元数据缺归属时仍可播放且再缓存时补上归属、断点续传（已写过的字节不再要第二遍，拼出来的文件与一次写完的完全一致）、取消保留进度、半截文件过长时重写、元数据与文件大小不符时当场清掉、多档时取上限内最高的那一档、删除与清空、空间判断；端到端的一条是：按在线播放的方式取字节（同一次索引解析、同一次解密）、落盘、再从缓存不带任何密钥地读回来逐段比对，并确认缓存文件里已经是可解码的索引（`encv`/`sinf` 被还原成 `avc1`，样本是解开的而不是原始密文）。logcat 搜索 `Episode cached` / `Episode cache failed` 可确认每集缓存结果与失败原因。

未验证：实际电视上的下载速度、离线播放的连续性与遥控器上的缓存操作手感需要用户安装测试包验收。缓存下载与正在在线播放的那一集共用带宽，整部剧缓存期间当前播放可能缓冲更慢，这一轮没有为它加专门的调度；离线缓存也不参与自动连播之外的跨剧集预取。

## 构建环境

需要 JDK 17、Android SDK Platform 36 和对应 Build Tools。设置 `JAVA_HOME`、`ANDROID_HOME`，或在本地 `local.properties` 配置 SDK 路径。可以用 Android Studio，或在支持 Android/Gradle 的 IDEA 中打开本目录；也可直接使用终端。

以下命令均从仓库根目录执行：

```sh
# 回归检查和开发 APK
./kotlin-tv/gradlew -p kotlin-tv :core:test :app:testDebugUnitTest :app:assembleDebug :app:lintDebug

# 只生成开发 APK
./kotlin-tv/gradlew -p kotlin-tv :app:assembleDebug
```

默认产物：`kotlin-tv/app/build/outputs/apk/debug/app-debug.apk`。

推送到 `main`、`feature-*` 或 `fix-*` 分支时，GitHub Actions 会执行同一组检查并生成可安装的调试 APK，文件名带分支名和提交短哈希。同一次 push 的 APK 会自动发布成一条预发布 Release：标题为「调试构建 <分支> <提交>」，正文列出分支、提交、versionName/versionCode、本次改动、自动化检查结果与安装说明；同一提交重复构建时更新既有 Release 与附件，不新建标签。这些 Release 不标记 Latest，也不进入 App 内的自动更新通道，只用于本机安装验证，不是发布版本。

正式包不在本机构建：在合并完成的 `main` 上打 `kotlin-v<版本>` 标签并推送，`.github/workflows/release-tv.yml` 会跑完全部检查、用同一把缓存签名密钥构建 `:app:assembleRelease`、核对包名／版本／minSdk、生成 `update.json` 与中文更新说明（详细日志取自仓库里的 `release-notes/<标签>.md`），然后发布为正式 Release（标记 Latest，进入 App 内的自动更新通道）。

## 版本与签名

修改 `app/build.gradle.kts` 中 `versionCode`、`versionName` 后重新构建。环境变量 `HONGGUOTV_VERSION_CODE`、`HONGGUOTV_VERSION_NAME` 会覆盖文件中的默认值。正式上线时递增版本号与 versionCode，编译调试期间保持不变，测试包通过文件名区分；当前正式版为 0.1.8（versionCode 49），后续正式发布再递增。分支名、APK 文件名或 Git 标签不会自动改变 APK 内部版本，标签只决定发布哪一份已经写好版本的源码。

开发 APK 使用 Debug 签名。电视已经安装的版本只能由相同包名、相同签名的新版覆盖；换电脑或改用其他签名可能无法覆盖安装。CI 构建共用一份缓存在 Actions 缓存里的 Debug 签名密钥（`~/.android`，缓存键 `hongguotv-debug-keystore-v1`），因此同一仓库的多次 CI 构建产物可以互相覆盖安装；该缓存被清理后会重新生成密钥，此时需要先卸载旧应用再安装。正式包同样使用这份缓存密钥：`release-tv.yml` 先构建 Debug 包确保密钥存在，再把它作为 `delivery` 签名配置传给 `:app:assembleRelease`，所以已安装调试包的设备可以直接覆盖安装正式版并保留本机数据。不要删除、替换现有签名密钥，不要将密钥或密码提交到仓库。

Release 构建读取 `kotlin-tv/keystore.properties`（已忽略）或对应环境变量：

| 本地配置字段 | 环境变量 |
| --- | --- |
| storeFile | HONGGUOTV_KEYSTORE |
| storePassword | HONGGUOTV_STORE_PASSWORD |
| keyAlias | HONGGUOTV_KEY_ALIAS |
| keyPassword | HONGGUOTV_KEY_PASSWORD |

`storeFile` 建议填写已有密钥的绝对路径。配置正确且确认签名连续后，可执行：

```sh
./scripts/build-kotlin.sh
```

脚本执行测试、Release lint、Release 构建，从实际 APK 读取版本和最低系统，计算大小与 SHA256，自动在 `outputs/releases/<tag>/` 生成配套 APK 和 `update.json`。需要 Python 3，以及 Android SDK 中的 aapt。它不会推送代码或创建 GitHub Release。发布完整步骤见 [AUTO_UPDATES.md](AUTO_UPDATES.md)。

## 验证边界

框架回归覆盖 API 23、API 26。具体电视的解码、声音、遥控器和实际账号同步仍需要设备验证。由维护者改代码、自动化检查和打包，用户安装测试并反馈截图；不自动操作用户模拟器。

竖屏与横屏视频都按设备解码能力选流：启动时探测 AVC/HEVC 解码器上限（logcat 搜索 `Decoder capabilities`），选流优先跳过盒子声明解不了的档位，并在播放前用 MP4 头里的实际编码尺寸复核，超出上限时自动沿清晰度阶梯降档（HUD 显示"自动降清"）。部分盒子会虚报解码能力（声明可解、实际失败）：此类运行时失败会按"编码+编码尺寸"记入持久化的设备能力记录（跨重启、跨剧集生效，竖屏失败不影响横屏），并当场自动降档重试（每集至多 2 次，无需手动切换），logcat 出现 `Learned decoder failure` / `Auto downgrading`。全部档位都不可解时保持原"兼容资源"行为交由系统尝试；播放失败面板的"尝试 xP"只在确有更低档位时出现；"播放设置 → 重置设备能力记录"可清除学习结果（应对盒子固件升级）。

播放中持续监测视频帧处理偏移（logcat 搜索 `Video frame offset` / `Resync after audio/video drift`）：平均偏移持续超过 150ms 时自动对当前位置做一次无感重同步（间隔至少 30 秒），用于消除随播放时长累积、倍速下更快的音画不同步。

自动连播开启时，当前集仍在播放就提前打开下一集：解析播放地址、按解码能力选档、读取 MP4 索引，再预热 2 MiB 媒体样本（移动数据 1 MiB），完成后直接加入播放器的媒体队列，本集结束即接续到下一集，不再重新取址。开始时机：Wi-Fi 在剩余 30 秒内、移动数据在剩余 60 秒内；两者都要求当前集已稳定播放 1.5 秒以上且缓冲领先足够（Wi-Fi 5 秒、移动数据 2.5 秒），以免预热抢占正在播放的一集。失败时按冷却重试（Wi-Fi 15 秒、移动数据 8 秒），每集至多 3 次（移动数据 4 次）。切到下一集时若该集的预热仍在进行，最多等 1.5 秒复用它，而不是再取一次地址；Wi-Fi 与移动数据之间切换不会丢弃已经预热好的下一集，只有网络真正断开才取消。logcat 搜索 `Next episode opening`、`Episode transition`、`Playback queue transition`、`Playback ready episode`（`carried=` 表示复用了预热）与 `Playback first frame episode` 可确认走的是哪条路径。队列里的下一集可能在本集切换生效之前就渲染出首帧，此时日志是 `Next episode rendered its first frame before the queue switch`，它属于下一集，不代表当前一集卡住。预热没落地时日志区分两种情况：`Next episode warmup cancelled by an episode change`（被切集或导航取消）与 `Next episode warmup failed: 异常类型`（真的取址失败）。实际衔接速度受网络与设备影响，仍需设备实测。

播放接口只认「服务端注册过的 `device_id` + `iid`」这一对身份：没注册过的身份一律回 HTTP 200 + 0 字节，看起来和"网络没问题但播不了"一模一样。所以第一次取播放地址前会先做一次匿名设备注册（`POST /service/2/device_register/`，不需要账号、密码或短信），拿到服务端下发的这两个 id 再取流；同一个应用进程内首页试播、正式播放和换剧切集共用这一份身份，既不本地随机生成，也不因某次播放失败轮换。注册响应里的设备 Cookie（`install_id`、`ttreq`、`store-region`、`store-region-src`）按白名单显式随播放请求发出：注册域与播放域是不同子域，这些 Cookie 没有跨子域可见的 `Domain`，交给 CookieJar 按域匹配发不出去，光"注册成功"照样会拿到空响应；账号类 Cookie 一律不转发。注册失败不会拿随机身份硬播（随机身份必然是空响应），而是显示"播放设备注册失败"并可重试；启动、浏览与搜索不依赖注册。

播放失败面板新增「查看原因」，把整条证据链直接画在屏幕上，不需要 logcat：失败步骤与异常类名、接口给出的每一档清晰度的编码与分辨率以及本机能不能解、本次实际尝试的清晰度与自动降清次数、当前播放身份是否已由服务端注册、本机枚举到的解码器列表。面板状态行同样附上异常类名，截图即可反馈。

播放地址接口偶发返回 HTTP 200 空响应，与榜单页被 CDN 软拦截是同一类现象。`streamLadder` 对空响应、超时与 5xx 先做至多两次同一查询的重试，仍然失败才报成播放失败；logcat 出现 `Playback failure: EmptyPlaybackResponseException` 说明重试之后仍没取到地址。

触屏设备（手机或带触控的电视）在播放页增加轻点显示／隐藏控制层、双击画面中间暂停／继续、双击左右两侧快退／快进 10 秒、按住画面任意区域临时 3 倍速（松手恢复默认倍速）和拖动进度条跳转；用户暂停时画面中央绘制暂停图标（选集面板打开、定时停止和播放失败时不显示）。面板按钮合并为一行——暂停、上一集、下一集、选集、防误触锁、播放设置、弹幕设置、评论，窄屏时该行可横向滑动——并新增防误触锁按钮：锁定后双击、长按倍速与进度条拖动都不再生效，仅保留面板开关以便解锁；状态行会显示"已锁定"。进度条仅在触屏设备使用可拖动的 SeekBar，电视上的进度条外观与焦点顺序不变。遥控器暂停改为确认键按两次（第一下只唤出控制层，600ms 内第二下生效），其余按键路径未改动。该触屏路径按系统是否声明触屏能力开启。双击判定、长按倍速、面板按钮布局和进度条拖动的手感仍需手机实测。
